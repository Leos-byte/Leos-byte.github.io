最近我把 Hermes Agent、多个专业 Agent、Kanban 和飞书放进同一套工作流。体验很直接：飞书让人随时发起任务、查看结果、补充意见；真正决定协作是否可靠的，却是飞书背后的任务状态、责任人、验收标准和发布闸门。

先说明证据范围：下文写“我遇到”“我们改了”的地方，都是我的个人使用经验，不代表 Hermes Agent 的普遍表现；写到产品行为时，我引用官方文档。很多问题来自我们的流程和配置，而不是产品缺陷。

## 先做一个判断：飞书是入口，不是多 Agent 公司的操作系统

Hermes 官方的飞书集成已经覆盖私聊、群聊、定时任务结果，以及文字、图片、音频和文件；群聊默认还会按用户隔离会话历史。[4] 这些能力很适合把 Agent 放到团队每天使用的界面里。

但消息界面回答不了四个关键问题：谁对最终结果负责？旧任务何时失效？什么证据才算完成？谁有权发布？这些问题必须由飞书背后的任务系统、权限和人工决策来回答。否则，聊天越顺畅，错误越容易显得像共识。

## 1. 没有单一负责人，多个 Agent 会做出“委员会式成品”

我最先踩的坑，是让多个角色都对网站结果发表完整意见。每个 Agent 的局部建议可能都合理，合在一起却会出现重复主张、信息层级混乱和语气不一致。参与者变多，没有自动带来更好的整合。

这不是 Hermes 的平台限制，而是我们的职责设计有问题。后来我把每项工作改成一个 DRI（直接负责人）：技术文章由 CTO Agent 负责，产品页面由 CPO Agent 负责，其他角色只交付明确输入，不再共同改同一个成品。

还没有完全解决的是跨领域冲突。单一负责人能减少拼接，但不能替 CEO 决定“增长优先还是风险优先”。遇到这种取舍，我现在要求 Agent 明确列出冲突，停在决策点，而不是用折中句把分歧藏起来。

## 2. 我改了角色说明，已经打开的会话却不会自动变成“新员工”

我曾以为更新角色、记忆或技能后，正在飞书里持续对话的 Agent 会立即采用新规则。实际并非如此：旧会话仍带着原来的上下文继续运行。Hermes 官方文档说明，Gateway 会话不会因闲置自动重置，要用 `/new` 或 `/reset` 建立明确边界；`MEMORY.md` 和 `USER.md` 在会话开始时注入。[2] 新安装的技能也默认在新会话中生效，若要进入当前会话，需要重置或主动使提示词缓存失效。[3]

因此，这一项主要是文档明确的会话模型，不应写成产品 bug。我们现在把重大角色调整、权限变化和工作规范升级都当作“新会话事件”：先结束旧任务，再重置会话，并用一个小任务确认新规则确实生效。

未解决的问题是长期会话中的渐进变化。压缩上下文能降低长度，却不等于重新确认所有治理规则。高风险任务仍需要在任务正文里重复关键约束，不能只相信某次角色更新已经被所有会话读到。

## 3. CEO 改了方向，不代表旧任务会自己消失

当我改变网站方向后，队列中按旧方向创建的任务仍可能继续等待或执行。Agent 并不知道一条新消息是否是在补充旧目标，还是正式撤销旧目标。若没有显式处理，最终会出现“新方向已经定了，旧任务还在产出”的情况。

这是我们的编排问题。Hermes Kanban 本来就是持久任务队列：任务有明确状态，父子依赖也会决定子任务何时从等待进入可执行状态。[1] 持久化的价值正是任务不会因一段新聊天而悄悄消失；反过来，方向变化时也必须由人或编排器显式取消、替换或重写任务。

我们现在把方向变更做成一次队列审计：找出所有未完成任务，逐项标记“继续、改写、取消”，再创建新任务。仍未解决的是自动识别语义冲突。现阶段我宁愿让系统提示“可能过期”，也不让模型自行删除任务。

## 4. 构建成功、DOM 正常，不代表读者看得懂

另一个明显教训来自网站验收。构建和链接检查都通过，DOM 结构也正确，但页面仍可能有中文断行难看、移动端表格难读、首屏重点不清或内容密度过高的问题。机器检查证明页面能生成，不证明人在真实屏幕上能理解。

这不是 Hermes 的限制，而是我们早期验收标准太窄。现在每次公开页面改动都要增加桌面与 320px 移动端的真实浏览器检查，并单独回答：第一屏在说什么？读者能否看懂这是给谁的？链接、表格和长 URL 是否可用？

仍未解决的是“看得懂”不等于“愿意购买”。浏览器审查只能发现渲染和理解问题，不能代替真实用户访谈、转化数据或市场验证。

## 5. 收到“任务完成”通知，不等于外部已经发布成功

飞书中的完成通知很容易制造一个错觉：Agent 说完成了，事情就已经对外生效。实际上，任务可能只完成了本地文件、提交或内部审核，远端分支、CI、Pages 和线上 URL 仍是另一组状态。

Hermes 文档区分 `local-only` 与 PR completion contract。后者会检查 PR、目标 SHA 和 required checks；文档也明确提醒，本地验证和“已经发布”都不等于远端验收。[1] Kanban 的飞书通知只是在同一会话里报告任务完成或阻塞，它不是外部系统的发布证明。[1]

我们的改法是拆成两道闸：实现 Agent 只提交本地候选；独立发布任务再检查远端提交、CI、部署记录和线上页面。通知中必须写明“完成的是哪一层”。尚未解决的是所有外部系统的一致事务：数据库写入、GitHub 状态和网页生效无法天然原子化，所以发布后仍要回读目标系统。

## 6. 限流和错误的交付契约，会让状态看起来比实际更严重

我还遇到过一种很误导人的状态组合：上游模型限流，任务被重新排队；同时任务配置了不适合它的交付契约，重试后又无法按那个契约完成。表面看像 Agent 一直失败，实际包含两个不同问题。

官方文档规定，provider 限流、过载、5xx 或超时会被记为 `rate_limited` 并重新排队，而且不计入普通失败；不可恢复的凭据或模型配置错误则会触发阻塞。[1] 这是平台的恢复机制。我们配置了错误的交付契约，则是自己的问题，不应归因给限流或调度器。

现在我们把故障分三类：临时资源问题自动重试；配置错误直接阻塞并要求修正；交付契约在创建任务时就区分本地工件、PR 和线上发布。仍未解决的是状态展示对非技术读者不够直观——“排队、阻塞、失败、等待人工”需要在通知里翻译成下一步动作，而不是只报内部状态名。

## 7. Agent 有进度，不等于公司已经作出决定

最后一个坑最容易被忽略。Agent 可以完成研究、生成代码、跑测试、给出推荐，Kanban 也能显示清晰进度；这些都不是人的授权。特别是定位、预算、公开承诺、发布和真实客户数据处理，不能因为多个 Agent 给出一致意见就自动通过。

这一项属于我们的治理选择。现在我把每个状态分成两类：可由证据关闭的执行状态，以及必须由人确认的决策状态。前者可以用测试、截图、链接和日志验收；后者必须留下明确的人类决定，Agent 只能准备选项和风险。

仍未解决的是人的注意力本身。审批点太多会让流程停滞，太少又会让系统越权。接下来要优化的不是“让 Agent 更像管理者”，而是只保留真正高风险、不可逆和对外承诺的人工闸门。

## 我现在采用的最小做法

如果你也准备用飞书管理多个 Agent，我建议先做六件事：

1. 每个成品只设一个 DRI，其他 Agent 只提供边界明确的输入；
2. 角色、记忆、技能或权限发生重大变化后，新开会话并做一次小范围验证；
3. 方向改变时审计所有未完成任务，不依赖聊天消息自动覆盖旧队列；
4. 把构建、DOM、桌面视觉、320px 视觉和读者理解分开验收；
5. 区分“本地完成、远端通过、部署成功、线上回读”四种完成；
6. 在任务创建时写清交付契约，并把人工决策与 Agent 执行分开。

我的结论不是“Hermes 不适合多 Agent 协作”。相反，持久任务、会话、角色和飞书入口让这套系统具备了可用的骨架。真正的难点是：这些能力不会替你决定责任、撤销旧目标、定义证据或承担授权。飞书把协作带到人面前；要让它变成可靠的公司工作流，还需要任务状态、单一所有权、独立验收和明确的人类闸门。
